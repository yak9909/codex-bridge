# codex-bridge v0.2 設計書

- 作成日: 2026-11-14
- 状態: 承認待ち
- 前の版: [2026-11-14-codex-bridge-design.md](2026-11-14-codex-bridge-design.md)（v0.1）

用語: **使う側**＝依頼する人（host を動かす）、**使わせる側**＝Codex を貸す人（agent の exe を動かす）。

## 1. 目的

v0.1 は「使う側 1 人・使わせる側 1 人・共有フォルダ 1 つ」を前提にしていた。v0.2 では次を満たす。

1. 使う側が、PC 内の好きなフォルダを**絶対パスで複数**登録し、それぞれ読む／書く／見せないを決められる。
2. 使う側に、**複数の使わせる側**がつなげる。新しい依頼は、**使用量に余裕のある人**に自動で振り分ける。
3. 使わせる側が、自分の PC で起きていることを**見て、決められる**。具体的には、作業の見える化、上限と止め方、事前承認、使い捨てセッション、保存場所、使える機能の制限。

## 3. 使う側（host）

### 3.1 複数の共有フォルダ（絶対パス）

**考え方:** 「共有ルート 1 つ＋中の規則」をやめる。代わりに「**許可するフォルダの一覧**」にする。一覧にない場所はすべて見えない。

```yaml
# policy.yaml（v2）
folders:                                   # 上から順に表示。最初のものが「メイン」
  - {path: "D:/work/project",          level: write}
  - {path: "D:/tools/common-lib",      level: read}
  - {path: "D:/work/project/secret",   level: hidden}   # 許可したフォルダの中を隠す
  - {path: "D:/work/project/vendor",   level: read}     # 書けるフォルダの中を読むだけに
exec: {...}                 # v0.1 と同じ
delete_needs_approval: true
paused: false
```

**判定の規則:**
- ファイル `X` の扱いは、`X` を含むフォルダの規則のうち**いちばん深いもの**で決まる。
  - **`hidden` は深さに関係なく常に優先**し、中身ごと隠す（v0.1 と同じ）。
- どのフォルダにも含まれない場所は「見えない」とする。存在しない場所と同じく `not found` を返す。
- Codex に渡すパス:
  - **絶対パス**（`D:/tools/common-lib/x.py`）をそのまま受け付ける。
  - 相対パスは**メインのフォルダからのもの**として扱う。v0.1 の依頼の書き方は、そのまま動く。
- 結果に出すパス:
  - メインのフォルダの中は、相対パスで返す（v0.1 と同じ）。
  - それ以外のフォルダの中は、絶対パスで返す。
- ジャンクション・シンボリックリンク・`..`・`:`（NTFS の別ストリーム）の扱いは、v0.1 と同じ。実際のパスに解決してから判定する。
- `list_dir("/")`（またはパスを省いたとき）は、登録したフォルダの一覧を返す。Codex が最初に全体を見渡すための入口にする。
- `find_files` と `grep` は、パスを省くと、見えるフォルダのすべてを対象にする。
- `run_command` の `cwd` は、`write` か `read` のフォルダの中に限る。
- コマンドの出力の保存先（`.codex-bridge/outputs`）は、メインのフォルダに置く（v0.1 と同じ）。

**移行:** v0.1 の `host.yaml` の `share_root` と、`policy.yaml` の `default` と `rules` は、起動時に v2 の `folders` へ自動で変換する。
- `share_root` に `default` の権限を付けて、メインのフォルダにする。
- 相対の `rules` は、`share_root` からの絶対パスにする。
- ワイルドカードを含む規則は、`advanced_rules` として残す。

**管理画面（「共有フォルダと権限」欄）:**
- 一覧の各行には、パス、プルダウン（読むだけ／書ける）、削除ボタン、展開ボタンを並べる。
  - 展開すると中のフォルダの木を出し、フォルダごとに「上と同じ／見せない／読むだけ／書ける」を選べる（v0.1 の木と同じ形）。
- 「フォルダを追加」ボタンで、パスを入力するか、「参照…」でフォルダを選ぶ画面を開く。
- メインのフォルダには印を付け、別のフォルダに切り替えられる。
- コマンド実行と削除の設定は、v0.1 と同じ。

**エージェントの道具:**
- 追加: `add_shared_folder(path, level)`、`remove_shared_folder(path)`、`set_main_folder(path)`。
- 変更: `set_folder_level(path, level)` が絶対パスも受け付けるようにする。
- 廃止: `set_share_root` は `add_shared_folder` と `set_main_folder` に置き換える。v0.1 の名前は別名として残す。

### 3.2 複数の使わせる側

**見分け方:** 使わせる側は、**招待コードの名前**で見分ける。招待コードは使わせる側ごとに発行する（v0.1 と同じ仕組み）。exe の側で何かを名乗らせる必要はない。

**host が使わせる側ごとに持つもの:**
- 接続状態
- exe と Codex の版、ログインの種類
- 使用量
- 使わせる側が決めた上限
- できること（使い捨てかどうか、事前承認の有無。§6）
- 作業中のタスク

**作業:**
- **使わせる側ごとに同時に 1 つ**とする。複数の使わせる側がいれば、並行して進む。
- Codex からの道具の呼び出しには、使わせる側ごとの合言葉が付いている。そのため、どの使わせる側のどのタスクの操作かを host が見分ける。取り消し用の保存、承認待ち、記録を正しいタスクに結び付ける。
- 受け口から届く通し番号の重複判定は、**使わせる側ごと**に行う（v0.1 は全体で 1 つだったので、複数だと衝突しうる）。

**管理画面:**
- 上部に「使わせる側」の表を置く。各行は、名前、接続状態、使用量のバー（5 時間枠・週間枠）、上限、作業中のタスク、事前承認の有無、使い捨てかどうか。
- 依頼の欄に「送り先」を置く。選べるのは、「自動（使用量に余裕のある人）」と、各使わせる側の名前。

### 3.3 新しい依頼の振り分け

新しい依頼で `send_task` の送り先が「自動」のとき、次の条件をすべて満たす使わせる側の中から、**余裕がいちばん大きい人**を選ぶ。

- 接続中
- 作業中ではない
- しきい値を超えて止められていない

**余裕**は、5 時間枠と週間枠のそれぞれについて「（その使わせる側に効く上限）−（今の使用率）」を出し、小さいほうをとる。
- その使わせる側に効く上限は、使う側のしきい値と使わせる側の上限のうち、低いほう。
- 使用量がまだ届いていない人は、余裕を最も小さいものとして扱う（最後に選ぶ）。
- 同じ余裕なら、最後に依頼した時刻が古い人を選ぶ。

**続きの依頼**（`continue_task_id`）は、**前のタスクと同じ使わせる側**にしか送れない。会話がその人の Codex の中にあるためである。次の場合はエラーとし、エージェントには「前回の報告を添えて新しく依頼する」ことを勧める文を返す。
- その人が接続していない
- その人が作業中
- その人のセッションが使い捨て

**エージェントの道具:**
- 追加: `list_lenders()`
- 変更: `send_task(prompt, continue_task_id?, lender?)` に送り先を加える。`get_usage()` は使わせる側ごとの値を返す。
- `get_guide` の手順を、複数の使わせる側に合わせて書き直す。

### 3.4 管理画面の作り直し（§5 の共通部品を使う）

- 上から順に、次のように並べる。
  1. 上部の帯（接続状態・全体の一時停止）
  2. 「使わせる側」の表（§3.2）
  3. 確認待ち
  4. 「Codex に依頼する」
  5. **タスク一覧＋詳細**
  6. 共有フォルダと権限（§3.1）
  7. 招待コード
- タスクの詳細は、§5 の「タスク詳細」部品で表示する。
  - 「簡易」と「詳細」を切り替えられる。
  - 誰（どの使わせる側）が担当したかを出す。
  - Codex の途中経過（§4.10）が、使う側でも見える。

## 4. 使わせる側（agent の exe）

### 4.1 画面（http://127.0.0.1:8766/）

**使う側の管理画面と同じ部品・同じ並べ方にする**（§5）。タブには分けず、1 ページの中を上から順に並べる。

| 順 | 欄 | 中身 |
|---|---|---|
| 1 | 上部の帯 | 接続先（使う側の名前）、接続状態、「一時停止」ボタン（管理画面の「全体を一時停止」と同じ位置・形） |
| 2 | 使用量 ＋ 状態 | 左に使用量のバー（§4.2）、右に今の状態（待機中／作業中／事前承認待ち／一時停止）と Codex・exe の版 |
| 3 | 事前承認待ち | 依頼文と「許可」「拒否」（管理画面の「確認待ち」と同じ形・同じ色）。B がオフなら出さない |
| 4 | **タスク一覧＋詳細** | 管理画面と同じ。左にタスクの一覧（状態の色札・依頼文の冒頭）、クリックで右に詳細（§5 の「タスク詳細」部品。簡易／詳細の切り替え・途中経過・最終報告） |
| 5 | セッション | このツールで作ったセッションの一覧（作った日時、関係するタスク、**作業中かどうか**、使い捨てかどうか）と**削除ボタン**（作業中は押せない）。セッションを選ぶと、そのセッションのタスクに絞って 4 を表示する |
| 6 | 設定 | §4.3〜§4.8（管理画面の「権限」欄と同じ、説明つきの選択肢の形） |

事前承認待ちが出たときは、タスクトレイの通知と、概要タブの目立つ表示で知らせる。

### 4.2 使用量のバー

使う側の管理画面と同じ形にする。
- 5 時間枠と週間枠のバー。使用率と、枠が戻る時刻を出す。
- **上限の線**も描く。線は、使わせる側の上限と、使う側から届いたしきい値の両方を描き分ける。
- 超えているときは色を変え、「止めています（○時まで）」と出す。

### 4.3 上限と止め方（v0.1 からの続き）

5 時間枠・週間枠の上限と、「超えたらすぐ強制的に止める」のチェック。v0.1 と同じ。
- **初期値を入れておく**（E）: 5 時間枠 80%・週間枠 80%・強制停止はオフ。初回起動で、この値を表示する。

### 4.4 使える機能の制限（D）

チェックボックスを置く。初期値はすべて「止める」。

| 機能 | 止める理由 |
|---|---|
| Web 検索・Web の取得 | 使用量。使わせる側のアカウントで外部にアクセスする |
| 画像生成 | 使用量 |
| サブエージェント（複数エージェント） | 使用量（並行して消費する） |
| 目標（goal）機能 | 使用量（長時間の自走） |

- 変えたときは、作業中でなければ Codex（app-server）を起動し直して反映する。作業中なら、作業が終わってから反映する。
- **作る前に確かめること:** それぞれを止める設定の正しい名前と、止めても bridge の道具が動くこと。v0.1 では `code_mode_host` を止めたら bridge が動かなくなったので、1 つずつ本物で試す。

### 4.5 事前承認（B）

- 設定は「使う側からの依頼を、私が許可してから始める」（オン・オフ。初期値はオフ）。
- オンのとき、新しい依頼と追加の指示は、**Codex に渡す前に止める**。
  - 概要タブに、依頼文と「許可」「拒否」のボタンを出す。
  - タスクトレイでも知らせる。
- 待つのは最長 30 分（変更できる）。過ぎたら拒否する。
- 使う側には、状態「**使わせる側の承認待ち**」（`awaiting_lender`）を送る。拒否したら「**使わせる側が拒否**」（`rejected_by_lender`）を送り、任意の理由も添える。
  - 使う側の管理画面とエージェントの道具は、この状態をそのまま見せる。

### 4.6 使い捨てセッション

- 設定は「セッションを使い捨てにする」（オン・オフ。初期値はオフ）。
- オンのとき:
  - Codex のセッションを `ephemeral: true` で始める。**本物で確かめた結果、会話の記録ファイル（`~/.codex/sessions/…`）は作られない。**
  - 依頼が終わったら（完了・中止・失敗・中断のどれでも）、そのセッションを捨てて、一覧からも消す。
  - 作業中の追加の指示は使える。終わったあとの「続き」は使えない。
  - 使う側には、接続時に「続きの依頼はできない」と知らせる（§6）。続きを頼まれたら、理由を付けて断る。
- 使用量の上限で中断した依頼も、続きはできない。使う側は、報告を添えて新しく依頼し直す（振り分けで別の人に行くこともある）。

### 4.7 保存場所（生成ファイル）

- 設定は「codex-bridge のデータの保存場所」。初期値は `%LOCALAPPDATA%\codex-bridge-agent`。
- ここに置くもの:
  - 招待コード（暗号化済み）
  - 設定
  - セッションの一覧
  - 記録（ログ）
  - 作業フォルダ
  - ダウンロードした Codex（`bin\`）
- 変えたときは、中身を新しい場所へ移し、exe を起動し直す。
  - 保存場所そのものは、`%LOCALAPPDATA%\codex-bridge-agent\location.txt` に記録する。これだけは移さない。
- **codex-bridge では場所を変えられないもの**（画面にそのまま書く）:
  - Codex 自身が `~/.codex` の下に書くもの: 状態の記録（sqlite）、ログ、モデルの一覧の控え、一時ファイル、通常のセッションの会話の記録。
  - 使い捨てにすれば、会話の記録は作られない。それ以外の小さな共有ファイルは残る。
  - 完全に分けるには Codex の設定フォルダ（`CODEX_HOME`）を分ける必要があるが、ログイン情報の扱いに未確認の点があるので、v0.2 ではやらない。
- PyInstaller が起動のたびに使う `%TEMP%\_MEI…` は、終了時に消えるので対象外とする。

### 4.8 作業フォルダの場所（H）

- Codex の作業フォルダ（空のフォルダ）は、初期値を `C:\ProgramData\codex-bridge-agent\work-<ランダム>` にする。
  - ユーザー名を含むパスが Codex の前提情報として渡り、使う側に漏れるのを防ぐ。
  - 作れない場合は、保存場所の中の `workdir` にする。
- 設定でパスを変えられる。

### 4.9 依頼文と最終報告は必ず見せる（C）

使う側の「知人に見せるログ」の設定に関係なく、次のものは使わせる側の記録に必ず残し、画面に出す。
- 依頼文・追加の指示・最終報告・状態の変化
- Codex の途中経過（§4.10 の「発言」と「計画」）

使う側の設定で絞れるのは、道具の呼び出しと、その引数・結果だけにする。

### 4.10 Codex の作業ログ（途中経過の記録）

v0.1 は、Codex の発言と道具の呼び出し（名前と引数の一部）だけを送っていた。v0.2 では、app-server の通知から次のものを**タスクごと**に記録する。

| 種類 | 元にする通知 | 中身 | 簡易表示 | 使う側へ送る |
|---|---|---|---|---|
| 発言（途中経過の報告） | `item/completed`（agentMessage） | Codex が書いた途中の報告・最終報告 | ○ | ○ |
| 計画 | `turn/plan/updated` | Codex の作業計画（手順と、それぞれの済み／作業中／未着手） | ○（最新のもの） | ○ |
| 考えていることの要約 | `item/completed`（reasoning の summary） | 推論の要約（中身そのものではない） | — | ○ |
| 道具の呼び出し | `item/started`・`item/completed`（mcpToolCall など） | 道具の名前・引数・かかった時間・成否・結果の要約 | — | ○（v0.1 と同じ） |
| 状態の変化 | `turn/started`・`turn/completed` など | 開始・区切り・完了・中断・失敗・事前承認・使用量による中断 | ○ | ○ |
| 使ったトークン | `thread/tokenUsage/updated` | ターンごとの入力・出力のトークン数 | — | ○ |

- 途中の文字ごとの通知（`…/delta`）は記録しない（量が多すぎるため）。ただし画面の「作業中」の欄には、書きかけの最新の発言を流して表示する。
- **記録先:**
  - 使わせる側では、保存場所（§4.7）の `logs/tasks/<task_id>.jsonl` に書く。
  - 使う側では、v0.1 と同じくタスクのイベントとして保存する。
- **表示の範囲:**
  - 使わせる側では、§4.9 のとおり「発言・計画・状態」は常に見せる。それ以外は、使う側の設定に従う。
  - 使う側では、すべて見える。
- **保管期間:** 使わせる側の記録は、初期値 30 日で古いものから消す（設定で変えられる）。使い捨てセッションでも、この記録は残す（会話そのものではなく、何が行われたかの記録のため）。消したい場合は「記録を消す」ボタンで消せる。

## 5. 画面の共通部品（使う側・使わせる側で同じものを使う）

両方の画面で、同じ CSS と JavaScript の部品を使う。部品は `codex_bridge/common/web/` に置き、host と agent の両方が同じものを配信する。見た目・言葉・色・並べ方をそろえる。

| 部品 | 中身 | 使う場所 |
|---|---|---|
| 上部の帯 | 製品名・画面名・接続状態の点・右端の一時停止ボタン | 両方 |
| カード | 白い枠の欄。見出しの書き方を統一する | 両方 |
| 使用量のバー | 5 時間枠・週間枠。使用率・戻る時刻・上限の線（複数の線を描き分け）・超過時の色 | 両方（使う側は使わせる側ごとに並べる） |
| 状態の色札 | 受付／作業中／完了／中断（枠切れ）／失敗／中止／接続待ち／使わせる側の承認待ち／使わせる側が拒否。色と言葉を統一する | 両方 |
| 承認待ちの欄 | オレンジの欄に内容と「許可」「拒否」 | 使う側（コマンド・削除）、使わせる側（事前承認） |
| **タスク一覧＋詳細** | 左に一覧、クリックで右に詳細 | 両方 |
| タスク詳細 | 見出し（状態の色札・担当・開始と終了の時刻・かかった時間）、依頼文、**作業中の欄（最新の計画と書きかけの発言）**、最終報告、記録（時系列）。**「簡易」と「詳細」の切り替え**（簡易＝発言・計画・状態、詳細＝道具の呼び出し・考えの要約・トークンも）と、種類での絞り込み・検索 | 両方 |
| 説明つきの選択肢 | ラジオボタンに太字の名前と灰色の説明を付けたもの（v0.1 の「コマンド実行」の欄の形） | 両方の設定 |
| 通知 | 承認待ちが出たときのブラウザ通知 | 両方 |

**言葉の統一:**
- 「タスク」「依頼」「承認待ち」「一時停止」「使用量」などの呼び方を、両方の画面と手順書でそろえる。
- 画面の中では、「使う側」は「依頼主」、「使わせる側」は「Codex を貸している人」と書く（相手から見て分かる言い方にする）。

## 6. 通信の約束事の変更

- `hello` に次を足す:
  - `protocol: 2`
  - `capabilities: {resumable: bool, pre_approval: bool}`
  - `limits: {five_hour, weekly, force}`
- `task_state` の状態に、`awaiting_lender` と `rejected_by_lender` を足す。
- `event` の種類（`kind`）に、次のものを足す（§4.10）。
  - `plan`: 計画の一覧
  - `reasoning_summary`: 考えていることの要約
  - `tool_started` と `tool_finished`: 道具の呼び出しの開始と終了。名前・引数・かかった時間・成否・結果の要約
  - `token_usage`: ターンごとのトークン数
  - `progress`: 書きかけの最新の発言。使う側には 2 秒に 1 回までにまとめて送り、記録には残さない
  - v0.1 の `tool_call` は `tool_finished` に置き換える。v0.1 の exe からの `tool_call` も、そのまま表示できるようにする。
- `settings`（host → agent）は v0.1 と同じ。

**互換性:**
- 新しい host に v0.1 の exe がつないだとき: `capabilities` がなければ「続きあり・事前承認なし」とみなして動かす。
- v0.2 の exe が v0.1 の host につないだとき: 動かないことがあるので、host は先に更新するよう案内する。

## 7. 作る前に確かめること

1. Web 検索・画像生成・サブエージェント・目標機能を止める設定の名前と、止めても bridge が動くこと（§4.4）。
2. `ephemeral` のセッションでの追加の指示（`turn/steer`）と、2 回目以降のターンの動き（§4.6）。
3. 一般ユーザーが `C:\ProgramData` の下にフォルダを作れること（§4.8）。
4. 複数の共有フォルダにまたがる `grep` の速さ（大きなフォルダを複数登録したとき）。

## 8. 作る順番（案）

1. **host: 複数の共有フォルダ**（§3.1）。exe の更新なしで先に出せる。
2. **host: 複数の使わせる側と振り分け**（§3.2・§3.3）。v0.1 の exe のままでも動く範囲で出す。
3. **exe v0.2: 設定・画面・使い捨て・事前承認・保存場所・機能の制限**（§4）。
4. 両方をまとめて v0.2.0 としてリリースする。

## 9. 作る人に任せること

- 振り分けで、同じ余裕の人が並んだときの順番の細部。
- 設定ファイルの形式（JSON か YAML か）。
