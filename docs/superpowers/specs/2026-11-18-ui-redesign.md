## 0. 利用者の要求（2026-11-18、原文に近い形で記録）

画面について:
- 情報量が多い。
- 使用量バーに使用量が入ると、なぜか長さが変わる。
- 「続きの依頼」の項目の意味が自明でない。
- 「超えたらすぐ止めて報告させる」の文言だと、強制終了のことだと勘違いする。
- コマンド実行の場所が分かりにくく、全体の設定と離れていて分かりにくい。
- 説明の文が長すぎ、冗長すぎる。AI 特有の冗長さやデザインの不均一さが目立ちすぎる。
- モデルの表示が多くて、レイアウトが崩れる（使う側の管理画面）。

進め方について:
- まずデザインを全て見直す。
- デザイン関連のスキルを入れ、芋づる式に UI デザインの資料を探し、世にある UI 設計・UX 設計を学ぶ。目標は、分かりやすくシンプルで、細かい設定は展開できるようにすること。
- デザインの確認は、機能を付けず、全ての状態を表示した確認用のものを作って行う。
- 利用者の案は鵜呑みにしない。それより良い案がないかを探す。
- フリーのアイコンなどを取得し、分かりやすくする。しつこくない程度に、分かりやすくアイコンを置く。
- 「こうするべきだった」といった失敗や軌道修正が起きても、それに執着して過剰に直さない。
- 過剰な実装など、提案や考えを反映しすぎない。柔軟性を損なわない。どうあるべきかをちゃんと考える。

## 0.5 画面を作ったら毎回確かめること（作業の手順）

前回、左下の余白の偏りを見落としたのは、撮った画面を「はみ出し・崩れ」でしか見ず、面の釣り合いを確かめる手順を持っていなかったため。撮影のたびに、次を上から順に確かめ、気づいたことを直してから人に見せる。

1. **目を細めて見る（squint test）**: 最初に目に入るのが、いちばん大事なもの（承認待ち・つながりの状態）か。強調は 1 か所か。（calvin-visual-design-layout.md:312「The squint test」）
2. **余白の偏り**: 節の中で、どこかに大きな空きができていないか。2 列に分けた所は、左右の高さが釣り合っているか（目安: 低いほうが高いほうの 8 割以上）。空きができたら、要素の置き場所を入れ替えるか、2 列をやめる。機械でも測る（`design/check-layout.js`）。
3. **揃え**: すべての要素が、ほかの何かと見えない線で揃っているか。左端の線の数は少ないか。（calvin…:422「Nothing should be placed on the page arbitrarily.」）
4. **近接**: 見出しや説明が、属する要素のすぐそばにあり、ほかの要素とは離れているか。要素の中の余白 ≤ 要素の間の余白になっているか。（calvin…:438; cieden-spacing-best-practices.md:336「internal ≤ external」）
5. **反復・一貫**: 同じ性質のものが同じ見た目か（ボタン・状態・見出し・余白）。（smarthr-visual-grouping.md:878）
6. **言葉**: 消しても分かる文はないか。同じものを別の言葉で呼んでいないか。（govuk-writing-for-user-interfaces.md:49, :53）
7. **隠しすぎ**: 全員が見るべきものを開く部品の中に入れていないか。開く部品を入れ子にしていないか。（govuk-accordion.md:133, :149）
8. **すべての状態と幅**: 空・1 件・多数・失敗・長い名前のときと、1280px・狭い幅で崩れないか。

## 0.7 1 つのアプリにまとめた形（2026-11-18 夜の要求を受けて。下の 4 節より優先）

確認用のページ: `design/mock-app.html`（前の mock-admin / mock-lender は置き換え）。

- **常駐**: `codex-bridge.exe` を起動するとタスクトレイに常駐する。トレイのアイコンを左クリックすると画面（ブラウザ）が開く。右クリックのメニューは「画面を開く」「一時停止／再開」「終了」と、1 行の状態だけ。トレイは状態と知らせのための場所で、機能の入口は画面に置く（ms-notification-area.md:44, :78）。
- **タブ**: 「使う」「貸す」「ログ」の 3 つ。数字は、そのタブで判断を待っているものの数（承認待ち）。
- **使う**: 承認待ち → 貸す人の一覧 → 依頼する → 依頼の一覧と詳細 → 共有フォルダ → 共通の設定。
  - 貸す人は 1 人 1 枚のカード。閉じていても、名前・状態・作業中の依頼・使用量のバー 2 本が見える（全員が毎回見るもの）。開くと、その人に関する設定と情報がすべて出る（Syncthing の端末一覧と同じ形: syncthing-gui-docs.md:7-10, :131）。
  - 開いた中は 2 つのまとまり: 「あなたが決める」（コマンド実行・招待コード）と「〇〇さんが決めている」（使わせるモデル・推論の強さ・本人の上限・事前承認・会話・版）。
  - コマンド実行の全体設定はやめる。人ごとに決め、招待するときにも選ぶ。許可リストと「書き換えたスクリプトは承認待ち」は全員共通のまま、共通の設定に置く。
  - 招待は一覧の最後の「貸す人を招待」のカード。
- **貸す**: 事前承認待ち → 使用量 → 依頼主の一覧 → 依頼の一覧と詳細 → この PC。
  - 使用量は 1 行に「バー・今の値・あなたの上限」を並べ、その下に「上限を超えたら」を 1 行。2 列に分けない（余白の偏りを作らない）。
  - 依頼主も 1 人 1 枚のカード。開くと、その依頼主への設定（使わせるモデル・推論の強さの上限・事前承認・会話・止める機能・道具の記録）がすべて出る。
- **ログ**: 使う側・貸す側の両方のログを 1 つの流れで出す。絞り込み（どちら側か・警告以上）、検索、下まで自動で送るか、書き出し、フォルダを開く（docker-desktop-logs.md:1959, :1977）。
- **カードの中の並べ方**: 「見出し | 値か操作」の 2 列の行を縦に積む（ラベルの列の幅は揃える）。左右に別の塊を並べないので、高さの偏りが出ない。
- **開く部品**: カードを開く部品は 1 段だけ。カードの中にさらに開く部品を入れない（govuk-accordion.md:149）。モデルの一覧は折りたたまずに、折り返して並べる。

## 2. 用語（1 つの意味に 1 つの言葉）

| 言葉 | 意味 | 使わない言い方 |
|---|---|---|
| 依頼主 | Codex を借りる側（host を動かす人） | 使う側・接続先・管理者 |
| 貸す人 | Codex を貸す側（agent を動かす人） | 知人・Codex を貸している人・接続先・送り先 |
| 依頼 | Codex に頼む 1 つの仕事（画面の一覧では「タスク」と同じもの） | — |
| 会話 | Codex の会話（続きを頼める単位） | セッション・スレッド |
| 承認待ち | 依頼主か貸す人の判断を待っている操作 | — |
| 上限 | 使用量の上限（依頼主の上限・本人の上限） | しきい値 |
| コマンド実行 | Codex が共有フォルダでプログラムを動かすこと | — |

画面の名前: 「依頼主の画面」「貸す人の画面」。

## 3. 文言の決まり

- 節の説明は 1 行まで。無くて分かるなら書かない。UI の動きを説明したくなったら UI を直す（govuk…:53）。
- 1 文 1 つのこと。「〜できます」「〜します」の常体寄りの丁寧語。「ください」は操作を頼むときだけ。
- ボタンは「何が起きるか」を動詞で: 「保存」「依頼する」「発行」「許可」「拒否」。
- 状態のラベルは名詞: 「接続中」「準備中」「未接続」「作業中」「完了」「失敗」。
- 値が無いときは空欄ではなく「—」（入力できない項目）か何も出さない（smarthr-empty-data.md:833）。
- 注意（⚠）は、危険が本当にある所だけ: 「コマンド実行は閉じ込めていません」。

## 4. 段の分け方

### 依頼主の画面

上部のバー（いつも）: 名前・つながっている貸す人の数・「一時停止」。

タブ「作業」（1 段目）:
1. 知らせの帯（あるときだけ）: 一時停止中／共有フォルダが未設定／policy.yaml の誤り。隠さない。
2. 承認待ち（あるときだけ、いちばん上）。コマンドの全文・場所・依頼名・「許可」「拒否」。
3. 貸す人: 1 人 1 行。名前と状態、使用量 2 本、作業中の依頼。行の「詳細」を開くと: 版・ログイン・事前承認・会話・本人の上限と止め方・モデルの一覧・コマンド実行のモード（全体と違うときだけ1 段目にも印）。
4. 依頼する: 依頼文・頼む相手・モデル・推論の強さ・「依頼する」。
5. 依頼の一覧と詳細。

タブ「設定」（2 段目）:
1. 共有フォルダ（一覧・追加・権限）。
2. コマンド実行: 全体のモード（4 つ）＋「人ごとの例外」（貸す人ごとに「全体と同じ／…」）＋自動で実行してよいコマンド＋⚠ の注意。
3. 削除: 承認待ちにするか。
4. 使用量の上限（依頼主の上限 2 つ）。
5. 貸す人の画面に見せる記録。
6. 招待コード。
7. 「policy.yaml を直接編集」（開く部品。中に入れ子にしない）。

### 貸す人の画面

上部のバー: 名前・つながっている依頼主の数・「一時停止」。

タブ「作業」:
1. 知らせの帯（一時停止中など）。
2. 事前承認待ち（あるときだけ）。
3. 使用量（2 本）＋本人の上限＋止め方（対で）。
4. 依頼主: 1 人 1 行（状態・作業）。
5. 依頼の一覧と詳細。

タブ「設定」:
1. 依頼主ごとの設定（依頼主を選んで編集）: 使える機能・使わせるモデル・推論の強さの上限・事前承認・会話を残すか・記録の見せ方。
2. 依頼主を追加（招待コード）。
3. 会話の一覧（削除）。
4. 共通の設定: 作業フォルダ・記録の保管・データの保存場所。開く部品「場所を変えられないもの」。
5. この PC の Codex と exe の版・ブラウザ通知。

## 5. 見た目（トークン）

- 色: 文字 `#1f2430`、薄い文字 `#5d6576`、線 `#dde1e8`、地 `#f6f7f9`、面 `#ffffff`、強調 `#0d6b62`（深い青緑、操作と選択だけに使う）、注意 `#a15c07`、危険 `#b42318`、良 `#1b7a4b`。
- 文字: `"BIZ UDPGothic", "Yu Gothic UI", "Meiryo", system-ui, sans-serif`（Windows に入っている UD 書体。Web フォントは使わない）。基本 14px、小 12.5px、節の見出し 16px、ページの見出しは置かない（タブが見出し）。数字は `font-variant-numeric: tabular-nums`。
- 余白: 4px の倍数（4・8・12・16・24・32）。節の間 32px、節の中のまとまりの間 16px。
- 枠（カード）は節の単位だけ。節の中は余白でまとめ、罫線は表の行の区切りだけ（smarthr-visual-grouping.md:919）。
- 角丸は 6px（入力・ボタン）と 10px（節）の 2 種類だけ。影は使わない。
- 強調する所は 1 つ: 承認待ちの帯（黄の地と左の太い線）。
- 開く部品は `<details>`。ラベルは中身を言う（「詳細」ではなく、行では「版・モデル・設定」）。入れ子にしない（carbon-disclosures-pattern.md:92）。

## 6. 部品の決まり

- ボタンは 3 種類: 主（強調色の地）、副（枠だけ）、危険（危険色の文字と枠）。大きさは 2 種類（通常・小）。
- 状態は丸と文字: 緑＝接続中・作業中、灰＝未接続・完了、黄＝準備中・承認待ち、赤＝失敗。
- 使用量のバー: ラベル（2.5em）・バー（残り）・値（4.5em、右寄せ）の 3 列を固定。依頼主の上限は実線、本人の上限は点線の縦線。戻る時刻はバーの下に小さく。
- 表は列を少なく、セルは最短の形（primer-data-table-guidelines.md:100, :112）。1280px で横スクロールが出ない。400px では行が縦に積まれる。

## 6.5 比べた別の形（採らなかった理由）

- **1 ページのまま、設定の節を畳む**: 長さは減るが、毎日見るもの（承認待ち・依頼）と、たまに変えるもの（権限・招待コード）が同じ縦の流れに混ざる。2 段目を「タブ」という扉にしたほうが、扉の名前が正直で場所も固定される（nielsen…:83, :85）。
- **貸す人の行を開くと、その人の設定まで全部そこで変えられる**: 設定が効く対象の近くにはなる（gitlab…:59）。ただし、コマンド実行は「全体のモード」と並べないと、どちらが効くか分からない（利用者の指摘そのもの）。行の詳細には「今の値」と「変える」への道だけを置き、変える場所は設定タブのコマンド実行の節に 1 つにした。
- **モデルを表の列で全部見せる**: 列が増え、1 行が縦に伸びる（primer…:100, :112）。数と既定だけを見せ、一覧は開く部品の中へ。
- **アイコンを全部の見出し・ボタン・状態に付ける**: 目が散る。節の見出し、主なボタン、知らせの帯だけにした（状態は丸の色と文字で足りる）。アイコンは Lucide（ISC ライセンス）を `design/icons.svg` にまとめた。

## 7. 実装の段取り

1. `design/` の CSS とページを利用者に見てもらい、了承を得る。
2. Codex が、本番の `common/web/ui.css`・各 `style.css` を `design/` の CSS に置き換え、`app.js`・`ui.js`・`settings.js`・各 `index.html` を確認用のページと同じ HTML を出すように直す。`test_web.py`・`test_ui.py` の文字列の検査も合わせて直す。
3. 全件テスト → opus の検査 → 本物の画面を撮って確認用のページと比べる。
