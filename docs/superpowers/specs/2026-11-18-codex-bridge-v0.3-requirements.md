# codex-bridge v0.3 の要求（利用者の言葉と、決まったこと）

作成: 2026-11-18。設計がぶれないように、利用者の要求をそのまま残す。設計書・計画はこの文書に従う。食い違ったらこの文書が優先する。

## 1. 利用者の依頼（原文）

> - なんのモデルを使うかを指定できるように。貸す側は制限も可能
> - タスクの詳細でなんのモデルが使われているかが分かるように
> - 使う側の管理画面で、貸している人ごとにコマンド実行の権限設定ができるように
> - Codexが承認やタスク終了した場合に、mcpで呼んでいるエージェントに伝わる仕組み（あるいはエージェント側でバックグラウンドタスクで監視できるような仕組み）

## 2. 知らせる仕組み（依頼の 4 番）— いちばん重要

### 2.1 利用者の言葉（会話より）

> 承認待ちのときにエージェントが判断して許可、ユーザーの確認が必要なら許可する前にユーザーに問います
> 作業が終わったら結果を確かめて次の依頼に進みます
> そして一番重要なのは、出来事のたびにエージェントが進行中か承認待ちか終了かを判断しない仕組みです
> 特に、進行のたびにエージェントが確かめると莫大なトークンを無駄に消費します。

> 私はただ、エージェントがcodex-bridgeを利用する際に、承認待ちと終了のときにエージェントに伝わるようにしたいだけですが、なぜこんなに複雑になりますか？

> Claude CodeやCodexは元々何か指示をしなくても、勝手にユーザーの判断が必要かどうかを判断して確認します。codex-bridgeからの承認待ちが来たとき、自然にユーザーに確認するべきかAIの判断でそのまま承認するかを選ぶことができるべきです

> （send_task が終わるまで待つ案に対して）サブエージェントに依頼してメインエージェントは別の作業をするなどという分担ができないのではないですか？

> （サブエージェントに待たせる案に対して）それだとわざわざサブエージェントを呼ぶことになり、トークンを無駄に消費します。Claude Codeがサブエージェントを呼び出すように、自然にcodex-bridgeを使えるようにできないのですか？

> Claude Codeには、バックグラウンドタスクというものがあり、これは複数実行することができます
> そして、タスクがどれか一つ完了するたびにClaude Codeが起こされます
> send_taskをバックグラウンドタスクとして呼び出せれば、複数send_taskを呼び出しても、呼び出した側のエージェントは終了を待ったり、その間にやれることをやったりなど柔軟な対応が可能になるはずです

> （文書化のあと）見張りのコマンドを起動するだけで私の要求を満たせるのであれば、それも検討できます。
> サーバー側のタスクとありますが、この方式にすることによるデメリットなども知りたいです
> CodexもClaude Codeと同様に私の要求を満たせる設計にしたいです

### 2.2 求めていること（上の言葉から）

- エージェントに伝わるのは **承認待ち** と **終了** のときだけ。途中の出来事（道具を使った、ファイルを読んだ など）でエージェントを起こさない。
- 待っている間、エージェントはトークンを使わない。状態を何度も問い合わせる（ポーリングする）作りにしない。
- `send_task` を Claude Code の**バックグラウンドタスク**のように使える。複数を同時に出せて、どれか 1 つが承認待ちか終了になるたびに呼んだエージェントが起こされる。待っている間、エージェントは別の作業をしてよいし、ただ待ってもよい（エージェントが自分で選ぶ）。
- **サブエージェントを呼ばなくても**、メインのエージェントがそのまま使える。
- 承認待ちが届いたら、エージェントは**いつもどおり自分で**「そのまま許可する」か「利用者に確認する」かを選ぶ。codex-bridge から判断の仕方について特別な指示を出さない。そのため、承認待ちの知らせには判断に要るもの（コマンドの全文・削除するパスなど）を載せる。
- 終了が届いたら、エージェントは結果を確かめて次の依頼に進める。
- **Codex が呼び手のときも、Claude Code と同じように上の要求を満たす**（「待つだけ」で妥協しない）。
- 見張りのコマンドは、**起動するだけで**上の要求を満たせるなら候補に戻してよい。

### 2.3 してはいけないこと（失敗とみなすもの）

- 進行の出来事ごとにエージェントが起こされる、または状態を確かめに行く作り。
- 待つためにサブエージェントを呼ぶことが前提の作り。
- 見張りのコマンドや待つための道具など、利用者から見て余計な仕組みが増える作り（利用者は「複雑すぎる」と言っている）。
- 承認の判断について、エージェントに codex-bridge 独自の決まりを押しつける作り。

### 2.4 決まった方向（2026-11-18、利用者が承認）

利用者の言葉:
> 試す前に、私の要求などを文書に残し、私の求める設計がブレないようにしてください
> まず調査をしてください
> 試して
> その方向で良いです。私の要求なども文書に追加で残してください

決まったこと（調査と試験の結果は `2026-11-18-codex-bridge-v0.3-notify-research.md`）:
- `send_task`・`send_followup`・`decide_approval` は、受け付けたらすぐ戻る（task_id などを返す）。
- `install-mcp.bat` で、呼び手にフックを入れる。エージェントは見張りのコマンドなどを何も起動しない。
  - **Claude Code**: 上の道具の `PostToolUse` に asyncRewake のフック。そのタスクが承認待ちか終了になるまで待ち、なったら中身を伝えて終了コード 2 で抜け、エージェントを起こす（何もしていなくても起きる。作業中なら作業のあとに届く）。複数の依頼はそれぞれ別に起こす。
  - **Codex**: `Stop` のフック。エージェントがターンを終えようとしたとき、この呼び手が出した依頼のうち、まだ知らせていない承認待ちか終了があればすぐ、なければ起きるまで待ち、`decision: block` で中身を渡して続けさせる。知らせる依頼が残っていなければ待たずに終わる。
- 承認待ちも終了と同じ形で知らせ、判断に要る中身（コマンドの全文・削除するパス・タスク・貸している人など）を載せる。許可するか利用者に聞くかはエージェントが自分で決める。
- 待っている間はトークンを使わない。途中の出来事では起こさない。サブエージェントは要らない。
- 分かっている制限（利用者に伝えた）: Codex は待っている間ターンが続いている扱いで、利用者が話しかけるには Esc で止める。Codex のフックは利用者が一度 `/hooks` で信頼する。対話の画面での動きは試験では未確認で、作ったあと利用者に一度試してもらう。

### 2.5 これまでに検討した方向（記録）

- （最初の提案。調査で取りやめ）MCP の「サーバー側のタスク」（MCP の版 2026-07-28 の tasks）で `send_task`・`send_followup`・`decide_approval` を受け付ける。呼ぶとすぐ「受け付けた」と返り、承認待ちか終了になったところでタスクが終わる。Claude Code の資料（https://code.claude.com/docs/en/mcp.md#mcp-tasks-that-run-on-the-server）では、これがバックグラウンドタスクとして扱われ、終わると知らせが届き、何もしていなければエージェントが自分から続きに取りかかる。
- この仕組みに対応していない呼び手（Codex など）には、ふつうの呼び出しとして承認待ちか終了まで待ってから返す。
- 使っているライブラリ `mcp` 2.3.0 は版 2026-07-28 とタスクのデータの形を持つが、サーバー側の処理は無いので自分で書く。
- 本番の作りの前に、使い捨ての小さな MCP サーバーで、利用者の Claude Code（Windows）で本当にバックグラウンドタスクになるか（すぐ戻る・終わると知らせが届く・2 つ同時に出せる）を確かめる。codex-bridge の本体には触らない。
- 2026-11-18: 利用者は方式を決める前に調査を指示した（見張りのコマンドの再検討、サーバー側のタスクの弱点、Codex でも満たす方法）。調査で、サーバー側のタスクは Claude Code でも公開ベータ・ターミナル版だけ・サブエージェント不可・承認待ちに合わない、Codex は未対応と分かり、取りやめた。
- 退けた案と理由: 見張りのコマンド（`host watch`）と待つための道具（`wait_for_event`）は複雑すぎる（利用者。ただし見張りのコマンドは「起動するだけで満たせるなら検討できる」と利用者が言い直した）。待たせるためのサブエージェントはトークンの無駄（利用者）。MCP から直接送る channels は試験的で、起動のたびに特別な指定が要る。2 分で自動的に裏に回る仕組みは、最初の 2 分エージェントが待たされる。

## 3. モデルの指定（依頼の 1・2 番）

- 依頼ごとに、使うモデルを指定できる。
- 貸す側（知人）は、使わせるモデルを制限できる。
- タスクの詳細に、実際に使われたモデルが表示される。
- 今の作り: agent は Codex の `thread/start` にモデルを渡していない（`src/codex_bridge/agent/appserver.py:207-222`）。知人の Codex の既定のモデルが使われる。
- 利用者の言葉（2026-11-18）:
  > 推論の強さも指定できるようにします。貸す側で制限も可能です
  > 規定は全モデル許可です。ただし、推論強度の規定はxhighまでです
- 決まったこと:
  - 依頼ごとに**モデル**と**推論の強さ**を指定できる（省略時は知人の Codex の既定）。`send_task` と管理画面の依頼の欄の両方。
  - 貸す側は、使わせる**モデル**と**推論の強さ**を制限できる。
  - 既定（知人が何も設定していないとき）: **全モデルを許可**、**推論の強さは xhigh まで**を許可。Codex 0.167 の段階は low / medium / high / xhigh / max / ultra（モデルごとに対応する段階が違う）。
  - 許されていないモデル・推論の強さを指定したら、送る前に使えるものを示して断る。送り先を自動で選ぶときは、指定を許している人の中から選ぶ。
  - タスクの詳細と `get_status` に、実際に使われたモデルと推論の強さを出す（Codex が途中でモデルを切り替えたらそれも反映）。
  - Codex の仕組み（確認済み）: `model/list`（モデルごとの `supportedReasoningEfforts`・`defaultReasoningEffort`・`isDefault`・`hidden`）、`thread/start` の `model`、`turn/start` の `model`・`effort`、`thread/start` の応答の `model`・`reasoningEffort`、通知 `model/rerouted`。

## 4. 人ごとのコマンド実行の権限（依頼の 3 番）

- 使う側の管理画面で、貸している人（知人）ごとにコマンド実行の権限を設定できる。
- 今の作り: コマンド実行のモード（off / allowlist / ask / all）と許可リストは全員に共通の 1 つ（`src/codex_bridge/host/policy.py:108`）。どの知人からのコマンドかは `CommandRunner.lender_fn` で分かる。
- 利用者の言葉（2026-11-18）: 「3番はおすすめの案Aにします」
- 決まったこと（案 A）: 知人ごとに**モードだけ**を選べる。「全体と同じ」（既定）/ off / allowlist / ask / all。許可リストは全員で共通のまま。管理画面の「Codex を貸している人」の欄で選ぶ。退けた案 B（知人ごとの許可リスト）は、必要になったら広げる。
