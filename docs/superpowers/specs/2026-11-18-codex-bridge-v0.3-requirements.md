# codex-bridge v0.3 の要求（利用者の言葉と、決まったこと）

作成: 2026-11-18。設計がぶれないように、利用者の要求をそのまま残す。設計書・計画はこの文書に従う。食い違ったらこの文書が優先する。

## 1. 利用者の依頼（原文）

> - なんのモデルを使うかを指定できるように。貸す側は制限も可能
> - タスクの詳細でなんのモデルが使われているかが分かるように
> - 使う側の管理画面で、貸している人ごとにコマンド実行の権限設定ができるように
> - Codexが承認やタスク終了した場合に、mcpで呼んでいるエージェントに伝わる仕組み（あるいはエージェント側でバックグラウンドタスクで監視できるような仕組み）

## 2. 知らせる仕組み（依頼の 4 番）— いちばん重要

### 2.1 利用者の言葉（会話より）

> 承認待ちのときにエージェントが判断して許可、ユーザーの確認が必要なら許可する前にユーザーに問います
> 作業が終わったら結果を確かめて次の依頼に進みます
> そして一番重要なのは、出来事のたびにエージェントが進行中か承認待ちか終了かを判断しない仕組みです
> 特に、進行のたびにエージェントが確かめると莫大なトークンを無駄に消費します。

> 私はただ、エージェントがcodex-bridgeを利用する際に、承認待ちと終了のときにエージェントに伝わるようにしたいだけですが、なぜこんなに複雑になりますか？

> Claude CodeやCodexは元々何か指示をしなくても、勝手にユーザーの判断が必要かどうかを判断して確認します。codex-bridgeからの承認待ちが来たとき、自然にユーザーに確認するべきかAIの判断でそのまま承認するかを選ぶことができるべきです

> （send_task が終わるまで待つ案に対して）サブエージェントに依頼してメインエージェントは別の作業をするなどという分担ができないのではないですか？

> （サブエージェントに待たせる案に対して）それだとわざわざサブエージェントを呼ぶことになり、トークンを無駄に消費します。Claude Codeがサブエージェントを呼び出すように、自然にcodex-bridgeを使えるようにできないのですか？

> Claude Codeには、バックグラウンドタスクというものがあり、これは複数実行することができます
> そして、タスクがどれか一つ完了するたびにClaude Codeが起こされます
> send_taskをバックグラウンドタスクとして呼び出せれば、複数send_taskを呼び出しても、呼び出した側のエージェントは終了を待ったり、その間にやれることをやったりなど柔軟な対応が可能になるはずです

### 2.2 求めていること（上の言葉から）

- エージェントに伝わるのは **承認待ち** と **終了** のときだけ。途中の出来事（道具を使った、ファイルを読んだ など）でエージェントを起こさない。
- 待っている間、エージェントはトークンを使わない。状態を何度も問い合わせる（ポーリングする）作りにしない。
- `send_task` を Claude Code の**バックグラウンドタスク**のように使える。複数を同時に出せて、どれか 1 つが承認待ちか終了になるたびに呼んだエージェントが起こされる。待っている間、エージェントは別の作業をしてよいし、ただ待ってもよい（エージェントが自分で選ぶ）。
- **サブエージェントを呼ばなくても**、メインのエージェントがそのまま使える。
- 承認待ちが届いたら、エージェントは**いつもどおり自分で**「そのまま許可する」か「利用者に確認する」かを選ぶ。codex-bridge から判断の仕方について特別な指示を出さない。そのため、承認待ちの知らせには判断に要るもの（コマンドの全文・削除するパスなど）を載せる。
- 終了が届いたら、エージェントは結果を確かめて次の依頼に進める。

### 2.3 してはいけないこと（失敗とみなすもの）

- 進行の出来事ごとにエージェントが起こされる、または状態を確かめに行く作り。
- 待つためにサブエージェントを呼ぶことが前提の作り。
- 見張りのコマンドや待つための道具など、利用者から見て余計な仕組みが増える作り（利用者は「複雑すぎる」と言っている）。
- 承認の判断について、エージェントに codex-bridge 独自の決まりを押しつける作り。

### 2.4 ここまでの方向（コントローラの提案。利用者は試す前の文書化を指示した段階で、方向はまだ承認されていない）

- MCP の「サーバー側のタスク」（MCP の版 2026-07-28 の tasks）で `send_task`・`send_followup`・`decide_approval` を受け付ける。呼ぶとすぐ「受け付けた」と返り、承認待ちか終了になったところでタスクが終わる。Claude Code の資料（https://code.claude.com/docs/en/mcp.md#mcp-tasks-that-run-on-the-server）では、これがバックグラウンドタスクとして扱われ、終わると知らせが届き、何もしていなければエージェントが自分から続きに取りかかる。
- この仕組みに対応していない呼び手（Codex など）には、ふつうの呼び出しとして承認待ちか終了まで待ってから返す。
- 使っているライブラリ `mcp` 2.3.0 は版 2026-07-28 とタスクのデータの形を持つが、サーバー側の処理は無いので自分で書く。
- 本番の作りの前に、使い捨ての小さな MCP サーバーで、利用者の Claude Code（Windows）で本当にバックグラウンドタスクになるか（すぐ戻る・終わると知らせが届く・2 つ同時に出せる）を確かめる。codex-bridge の本体には触らない。
- 退けた案と理由: 見張りのコマンド（`host watch`）と待つための道具（`wait_for_event`）は複雑すぎる（利用者）。待たせるためのサブエージェントはトークンの無駄（利用者）。MCP から直接送る channels は試験的で、起動のたびに特別な指定が要る。2 分で自動的に裏に回る仕組みは、最初の 2 分エージェントが待たされる。

## 3. モデルの指定（依頼の 1・2 番）

- 貸す側（知人）は、使わせるモデルを制限できる。
- タスクの詳細に、実際に使われたモデルが表示される。
- 今の作り: agent は Codex の `thread/start` にモデルを渡していない（`src/codex_bridge/agent/appserver.py:207-222`）。知人の Codex の既定のモデルが使われる。
- まだ決めていないこと: 作り方の案は未提示（知らせる仕組みのあとに相談する）。
