# codex-bridge 設計書

- 作成日: 2026-11-14
- 状態: 承認待ち（調査による見直し・確認役の読み合わせ済み）

## 1. 目的と背景

知人が自分の Codex（OpenAI Codex CLI）を使わせてくれる。こちらの PC にある作業フォルダ（10GB 未満、解析済みファイルと解析対象ファイル）を、知人の PC で動く Codex に遠隔で読ませ・書かせ・解析スクリプトを実行させたい。

- 依頼を出すのは、基本的にこちらの Claude Code。Claude Code が知人側の Codex に依頼を送り、結果を読む。
- 知人のアカウントの認証情報はこちらに持ってこない（アカウントの貸し借りにしない）。Codex は知人の PC で、知人のログインのまま動く。

## 2. 目標・目標外・避けたいこと

### 目標
- フォルダを丸ごと送らずに、Codex がこちらのファイルを普段どおり探し・読み・書きできる。
- こちらの PC での解析スクリプトの実行を、ほどほどの守りつきで許す。
- 権限（見せる範囲・書ける範囲・実行の扱い）を、動作中でもこちらから変えられる。
- Claude Code から、依頼・途中の追加指示（フォローアップ）・状態確認・結果取得・中止・使用量確認ができる。
- 知人側 Codex の 5 時間枠・週間枠の使用率がしきい値を超えたら、自動で「区切りのよいところで止めて報告して」と指示し、穏やかに中断させる。
- 知人の作業は「ソフトを入れる」「招待コードを貼る」だけで済む。

### 目標外
- 悪意ある相手を前提にした堅牢な隔離（知人は信頼できる人）。
- 複数の知人・複数の Codex の同時利用（将来の拡張としては妨げない）。
- ファイルの種類や数の制限。

### 避けたいこと（動いても失敗とみなす）
- 知人の Codex の認証ファイルをこちらへコピーするなど、アカウント共有になる形。
- 知人に設定ファイルを手で書かせること。
- 使用量のしきい値で Codex を強制終了し、作業の途中経過が失われること。
- 見せないと決めた場所の名前や中身が、一覧・検索・エラー文などから漏れること。

## 3. 制約

- こちら: Windows 10。ポート開放は基本的にできない。
- 知人: Windows。ソフトのインストールはできる。設定の手書きは難しい（知人が自分の Codex に設定を書かせることはできる）。
- 知人の Codex のログは知人も閲覧できる。どこまで見せるかはこちらで制御する。

## 4. 全体構成

```
[こちらのPC]                                          [知人のPC]
 Claude Code                                           codex-bridge-agent (exe)
   │ MCP (stdio or localhost HTTP)                       │  ├─ codex app-server を子プロセスで起動・操作
   ▼                                                     │  ├─ 使用量の監視としきい値での中断指示
 codex-bridge-host ◀── 制御用 WebSocket ───────────────┤  └─ 知人向けログ画面 (localhost)
   ├─ Claude 用 MCP（依頼・状態・使用量）                 │
   ├─ Codex 用 MCP（ファイル操作・実行）◀── MCP (HTTP) ──┘ Codex がこちらの道具を直接呼ぶ
   ├─ 権限の判定（設定は動作中に変更可）
   ├─ 実行の確認待ち・Web 管理画面 (localhost)
   ├─ 書き込み前の保存（取り消し用）
   └─ 全操作の記録
            ▲
            └─ 回線: Tailscale（ノード共有）
```

- 接続はすべて知人側からこちら側へ向かう。知人側でポートを開ける必要はない。
- アプリ層は回線に依存しない。つなぎ先 URL と合言葉（トークン）を招待コードに入れる。

## 5. 部品ごとの決まり

### 5.1 codex-bridge-host（こちらの PC）

Python で作る常駐プログラム。

**(a) Codex 用 MCP エンドポイント**（Tailscale 側のアドレスで待ち受け、トークン認証必須）

| 道具 | 内容 |
|---|---|
| `list_dir` | フォルダの中身（名前・種類・大きさ・更新日時） |
| `find_files` | ファイル名のパターン検索（glob） |
| `grep` | 中身の正規表現検索（ripgrep を使う）。件数・文字数の上限あり |
| `stat` | ファイルの大きさ・更新日時など |
| `read_file` | 行範囲またはバイト範囲で読む。一度に返す量に上限あり。バイナリは要約情報のみ／16 進の一部 |
| `write_file` | 新規作成・全体の書き換え |
| `edit_file` | 文字列の置き換えによる部分編集 |
| `apply_patch` | Codex が慣れている形式（`*** Begin Patch` 形式）のパッチ適用 |
| `move_path` / `delete_path` | 移動・削除（削除は既定で確認待ち） |
| `run_command` | コマンド実行（5.1(c) の規則に従う） |

- パスはすべて共有ルートからの相対パスで扱う。`..`・シンボリックリンク・ジャンクションで外に出られないよう、実パスに解決してから判定する。
- 「見せない」場所は、一覧・検索結果・エラー文のどれにも現れない（存在しないものとして「見つからない」を返す）。

**(b) 権限の規則**（`policy.yaml`。保存すると即時反映。Web 画面からも編集）

- パスごとに `hidden`（見せない）/ `read`（読むだけ）/ `write`（書ける）。後に書いた規則が優先。ただし `hidden` は書いた順番に関係なく常に優先し、そのフォルダの中身もすべて隠す。
- フォルダの移動・削除は、中に `write` でない場所が1つでもあれば拒否する（拒否の文言には、中の名前を出さない）。
- 全体の一時停止スイッチ（すべての道具が「停止中」を返す）。

**(c) 実行の規則**

- モード: `off`（実行不可）/ `allowlist`（一致すれば自動、それ以外は確認待ち）/ `ask`（毎回確認待ち）/ `all`（すべて自動）。既定は `allowlist`。
- 自動許可のパターン例: `python scripts/**/*.py *`。
- 作業フォルダは共有ルートの中に限る。時間の上限（既定 30 分）・出力の上限（既定 1MB、超えた分はファイルに保存して要約を返す）。
- 確認待ちは Web 画面で人が「許可／拒否」する。Claude Code は承認できない（自分で承認できると守りにならないため）。確認待ちが生じたことは、Claude 用 MCP の状態に表示する。
- 実行のあと、`write` 領域で変わったファイルを更新日時と大きさで調べ、記録する。

**(d) 取り消し**

- 書き込み・編集・移動・削除の前に、元のファイルを host のデータフォルダの `snapshots/<task_id>/` に保存する（共有ルートの外。Codex から見えず、書き換えられない）。
- 依頼（タスク）単位で、まとめて元に戻せる。
- コマンド実行による変更は保存の対象外（変わったファイルの一覧だけ残る）。これは既知の限界として受け入れる。

**(e) Claude 用 MCP**（localhost のみ）

| 道具 | 内容 |
|---|---|
| `send_task` | 依頼文を送り、`task_id` を受け取る |
| `send_followup` | 作業中のタスクに追加の指示を差し込む |
| `get_status` | 状態（待機・作業中・確認待ち・完了・中断（枠切れ）・失敗）と途中経過 |
| `get_result` | 最終報告・変更したファイル一覧・ログ |
| `cancel_task` | 中止（穏やかな中断を先に試し、応じなければ強制） |
| `get_usage` | 5 時間枠・週間枠の使用率と、枠が戻る時刻 |
| `set_thresholds` | しきい値の変更 |
| `undo_task` | タスク単位の取り消し |
| `list_sessions` | このツールで作った Codex のセッション（スレッド）の一覧 |
| `read_session` | セッションの会話内容を読む |
| `delete_session` | セッションを削除する（app-server の `thread/delete`） |

- セッションの操作は、このツールが作ったものだけに限る。agent は自分が作ったスレッドの ID を記録し、それ以外のスレッド（知人が普段使っているもの）は一覧にも出さず、読むことも消すこともできない。
- Codex の会話記録（読んだファイルの中身を含む）が知人の PC に残ることは受け入れる。

**(f) Web 管理画面**（localhost のみ）

- 権限の規則の編集、実行の確認待ちへの許可／拒否、タスクとログの閲覧、使用量の表示、しきい値の設定、知人に見せるログの範囲の設定、全体停止。

**(g) 記録**

- すべての道具の呼び出し（引数・結果の要約・判定）、実行したコマンドと出力、タスクの経過を JSON Lines で保存する。

### 5.2 codex-bridge-agent（知人の PC）

PyInstaller で 1 つの exe にまとめる。知人は Python 不要。

- 初回起動で招待コードを貼る → つなぎ先 URL・トークンを保存し、以後は自動接続・自動再接続。
- 知人の PC にはデスクトップ版の Codex しかない見込み。agent は起動時に `codex` CLI を探す。見つからなければ、知人の了解を得てから公式の Windows 版 CLI（GitHub の公式リリース）を取得して agent の専用フォルダに置く。未ログインなら `codex login`（ChatGPT ログイン）を起動して、知人にログインしてもらう。
- ログインは ChatGPT のプランである前提（5 時間枠・週間枠があるのはこの場合だけ）。API キーでのログインを検出したら、使用量による中断を無効にし、host に知らせる。
- 知人自身も同じ時間帯に Codex を使うことがある前提にする。使用量の枠は知人と共有になるので、しきい値は知人の分の余裕も見込んで決める（既定値の 90% / 95% はそのため控えめに見直してよい）。
- `codex app-server` を子プロセスで起動し、タスクの開始・追加指示・中断・使用量の取得を行う。
- Codex の起動設定（知人の `config.toml` は書き換えない。渡し方の順番は 7.2）:
  - こちらの Codex 用 MCP エンドポイントを MCP サーバーとして登録（URL と、環境変数経由のトークン）。
  - 作業フォルダは agent が用意する空のフォルダ。サンドボックスは読み取り専用。内蔵シェル（`shell_tool`）は無効にし、こちらの道具だけを使わせる。
  - 承認の問い合わせは知人の画面に出さない（Codex 側の承認は不要にし、承認はこちらの host で行う）。
- 依頼文の先頭に、短い前置きを付ける（「ファイルはこちらの道具で扱う」「パスは共有ルートからの相対」など）。
- 知人向けのログ画面（localhost）。表示する範囲は host から届く設定に従う（例: 依頼文と報告のみ／ファイル名まで／すべて）。

### 5.3 使用量としきい値による中断

1. agent は使用量（5 時間枠・週間枠の使用率と、戻る時刻）を一定間隔（既定 60 秒、作業中は各ターン終了時にも）で取得し、host に送る。
2. 作業中にどちらかの使用率がしきい値（既定: 5 時間枠 90%、週間枠 95%）を超えたら、agent が作業中の Codex に次の追加指示を送る: 「今の作業を区切りのよいところで止め、終えたこと・残っていること・次にやるべきことを報告してください。」
3. Codex が報告を返して止まったら、タスクの状態を「中断（枠切れ）」にし、報告と枠が戻る時刻を host へ送る。
4. 指示から一定時間（既定 10 分）たっても止まらなければ、最後の手段として中止する。
5. しきい値を超えている間、新しい依頼は受け付けず、戻る時刻を返す。Claude Code はその時刻まで待ってから、報告をもとに続きの依頼を出す。

### 5.4 通信

- 回線は Tailscale のみ。こちらの PC 1 台だけを知人と共有する（ノード共有）。知人は Tailscale を入れてアカウントを作る。
- 予備の回線は作らない（ドメインも Cloudflare アカウントもないため。アカウントなしの Cloudflare Tunnel は起動のたびに URL が変わり、招待コードが使えなくなる）。ただしアプリ層は回線に依存しない作りを保ち、あとから追加できるようにする。
- アプリ層のトークン認証を必ず行う。トークンは招待コードの発行ごとに作り、Web 画面から失効できる。
- 制御用は WebSocket（知人 → こちら）。Codex の道具呼び出しは MCP の HTTP 方式（知人の Codex → こちら）。

### 5.5 招待コード

- つなぎ先 URL・トークン・表示名を 1 行の文字列にまとめたもの（例: base64url の JSON）。host の Web 画面で発行する。

## 6. 技術の選択（こちらの判断）

- 両側とも Python 3.12 系。MCP は公式 Python SDK。HTTP・WebSocket・Web 画面は FastAPI と uvicorn。
- 検索は ripgrep（host に同梱）。
- agent は PyInstaller で exe 化。

## 7. 調査の結果（2026-11-14）

### 7.1 確かめられたこと
- **追加指示・中断・使用量**: `codex app-server`（stdio 上の JSON-RPC。既定の方式で実験扱いではない）に、`turn/steer`（作業中のターンに入力を足す。`expectedTurnId` が必要）、`turn/interrupt`（中断。ターンは `interrupted` で終わる）、`account/rateLimits/read`（使用量）と通知 `account/rateLimits/updated` がある。→ 5.3 の流れはそのまま実現できる。
  - 使用量の応答は `primary` / `secondary` の 2 枠で、それぞれ `usedPercent`・`windowDurationMins`・`resetsAt`（Unix 秒）を持つ。**どちらが 5 時間枠かは位置で決めつけず、`windowDurationMins`（300 = 5 時間、10080 = 週間）で見分ける。** 定期取得に加え、`updated` 通知でも判定する。
  - 応答の形は「不安定」と明記されている。agent は起動時に `codex app-server generate-json-schema` の結果と照らし、合わなければ host に警告を出す。
- **HTTP 方式の MCP**: Codex は `mcp_servers.<名前>.url` で HTTP 方式（streamable HTTP）の MCP サーバーに対応し、`bearer_token_env_var` で環境変数からトークンを渡せる。→ agent は環境変数にトークンを入れて app-server を起動する。トークンはディスクに書かない。
- **内蔵シェルの無効化**: `shell_tool` 機能を無効にできる（`--disable shell_tool` / `features`）。内蔵のパッチ適用（apply_patch）は無効化の手段が見当たらないが、読み取り専用サンドボックスと空の作業フォルダにより知人のファイルは書き換えられない。→ Codex はこちらの道具に頼るので、host の `apply_patch` 道具は**作る**（Codex が慣れた書式のため、編集の成功率が上がると見込む）。
- **Tailscale**: ノード共有は全プランで使える。共有された機器は既定で「隔離」され、知人側からこちらへは入れるが、こちらから知人側へは接続を始められない。→ 「すべて知人側からこちらへつなぐ」設計と一致する。招待リンクは未使用だと 30 日で切れる。

### 7.2 設計を見直したこと
- **設定の渡し方**: こちらの codex-cli 0.167.0 で確かめたところ、`codex app-server` は `-c key=value` と `--disable <機能>` を受け付ける。さらに `thread/start` も `config`（スレッドごとの設定上書き）・`developerInstructions`・`sandbox`・`approvalPolicy`・`cwd` を受け付ける。→ agent は起動時の `-c` / `--disable shell_tool` と `thread/start` の引数だけで設定を渡す。知人の `~/.codex/config.toml` は書き換えない。
- **代わりの方式として残すもの**: app-server の `thread/start` には実験的な `dynamicTools`（クライアントが道具を差し出し、呼び出しがクライアントに返ってくる）がある。これを使えば MCP の HTTP 口が要らず、制御用 WebSocket 1 本にまとめられる。ただし実験扱いなので、第一案は MCP のままとし、道具の中身は両方式から呼べる形に分けて作る。

### 7.3 比べて採らなかった方式
- **フォルダを同期して知人の PC で作業させる**（Syncthing・git など）: 10GB の転送が要るうえ、解析の実行はこちらで行う必要があるため不採用。
- **Codex 公式のリモート接続（SSH・app-server をこちらで動かす）**: app-server はファイルのある側で動き、ログイン情報もそこに要る。知人の認証情報をこちらに置くことになり、アカウント共有に当たるため不採用。
- **`codex exec-server`（Codex 内蔵の道具をこちらの PC で動かす）**: 理屈の上では Codex の本来の道具がそのまま使えて理想的だが、公式資料は OpenAI の Agents API 経由の使い方しかなく、CLI 単体での組み方は未公開・実験扱い。細かい権限の判定も挟めない。将来の候補として記録するにとどめる。
- **既存のファイル操作 MCP サーバー（公式 filesystem サーバーなど）の流用**: 「見せない」場所・動的な権限・実行の確認待ち・取り消しが必要なため、自作する。

### 7.4 残る注意点
- **規約**: OpenAI の規約は、アカウントを他人に使わせることを禁じていると読める。この設計は認証情報を渡さないが、こちらが知人の Codex を遠隔で動かす形なので、グレーであることに変わりはない。危険を負うのは知人のアカウントなので、知人にこの点を伝えて了解を得ておく。
- **WebSocket 版の app-server** は「実験的・非サポート」とされているため使わない（agent は stdio で起動する）。

## 7.5 読み合わせで決めたこと（こちらの判断）

- **実行の守りの範囲**: 知人は信頼できる人なので、`run_command` で動くスクリプトは OS による閉じ込めをしない。スクリプトは `hidden` の場所や共有ルートの外も読めるし、`read` の場所にも書ける。「見せない場所が漏れない」（2 章）は、ファイル操作の道具だけに当てはまる。実行には当てはまらない。これは既知の限界として、Web 画面にも明記する。
- **自作スクリプトの実行**: Codex が書いたスクリプトも、許可リストに合えば自動で実行してよい（解析用のスクリプトを書いて走らせる、という普通の流れを止めないため）。ただし、「タスク中に書き換えられたファイルの実行は確認待ちにする」設定を用意する。この設定は既定では切っておく。
- **実行は非同期にする**: Codex の MCP 呼び出しには時間切れがあるため、`run_command` は長く待たない。次の作りにする。
  - 一定時間（既定 60 秒）で終わればその結果を返す。
  - 終わらなければ受付番号を返し、`get_command_result` で問い合わせる形に切り替える。
  - 確認待ちも同じく受付番号を返す。
  - 確認待ちに返事がなければ、既定 30 分で自動的に拒否する。
- **タスクと会話**:
  - タスクは同時に 1 つだけ。
  - `send_task` は既定で新しいスレッドを作る。`continue_task_id` を指定すれば、前のタスクのスレッドを続けられる（枠切れのあとの再開に使う）。
- **枠が戻ったあとの再開**: host は戻る時刻を返すだけで、自動では再開しない。再開は Claude Code 側の運用で行う（週間枠なら何日も待つことがあるため）。

## 8. 作る人に任せること

- 画面の見た目、ログの保存形式の細部、内部の通信メッセージの形。
- 既定値（上限・間隔・しきい値）の微調整。
